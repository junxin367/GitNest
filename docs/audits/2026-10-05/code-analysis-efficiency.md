# 代码分析效率优化与验证

本轮覆盖文件发现与读取、内置解析、关系匹配与查询、LSP 协议、快照缓存、分析服务和关系图交互。保留任务开始时已有修改，没有提交或打包安装程序。上一轮的进度节流、通用交互及骨架优化不计入本轮成果。

## 实际应用结果

使用冻结的修改前生产构建和最终生产构建，在隔离 Electron profile 中运行真实 Git、IPC、utility 分析引擎及页面。夹具为 300 个 TypeScript/Java/Python 文件，冷分析产出 6,180 节点、11,340 边、60 请求链；每版本 3 次，顺序为 before / after / after / before / before / after。

| 场景 | 引擎中位耗时，前→后 | 点击至 ready 观测中位，前→后 |
| --- | ---: | ---: |
| 全量冷分析 | 226→140 ms | 514→402 ms |
| 全量热分析 | 184→98 ms | 388→263 ms |
| 等长编辑并恢复 mtime 后全量分析 | 184→87 ms | 388→266 ms |
| 单文件变动范围分析 | 74→66 ms | 264→264 ms |
| 修改后恢复全量范围 | 227→85 ms | 526→388 ms |
| 取消后重新分析 | 212→91 ms | 509→422 ms |

冷、热全量引擎中位耗时分别下降约 38% 和 47%。观测 ready 使用约 120ms 轮询，包含 Git 准备、IPC 和状态等待，不是逐帧屏幕响应时间。只有三次样本，不将此结果推广为所有工作区的固定提升。单文件变动分析没有稳定可见的总延迟收益，切换范围期间也可能提前恢复缓存。

六个阶段在六次应用运行中的完整图哈希均一致。哈希包含排序后的完整节点、边、请求链，以及 warnings/diagnostics；排除运行 ID、生成时间和耗时。热分析缓存命中 300 文件；等长且相同 mtime 的内容变更命中 299 文件，确认继续依据实际内容指纹失效。正常变动范围、搜索选点、缩放、取消、取消后恢复通过，renderer errors 为 0。已人工查看前后图截图，布局、选点和关系显示一致。

此次应用测试禁用了实际语言服务器，各版本均明确显示局部索引。它验证真实桌面内置分析流程，不能证明真实 TypeScript/JDT 等服务器的启动、导入和完整语义分析性能。

最初基线将“等长且恢复 mtime 的文件”直接用于 Git 变动范围；Windows 测试仓库的 Git status 未报告该变化，导致夹具假设失败。正式验证改为先用全量内容指纹检查此编辑，再使用常规编辑检查变动范围。原始失败日志保留，没有把该现象算作本轮修复。

## 保留的优化

| 环节 | 修改与行为约束 |
| --- | --- |
| 文件发现 | 使用有界并发，按原发现顺序消费；临近文件数/总字节限制时收窄批次，保持准入、截断和警告顺序。 |
| 源码读取 | 指纹读取的同一份已校验字节直接用于内置解析及 LSP 文档，消除冷分析二次读取；批次暂存约束为 8MiB 或一个受限文件。 |
| 内置索引 | 在发现期间逐文件解析；关闭语义阶段时不保存全部正文，热缓存跳过无用 UTF-8 解码。 |
| 读取收尾 | 只读最初确认的长度，检查读取前后完整精度时间和文件身份；分块检查取消，并等待在途句柄关闭。 |
| Java 解析 | 一次解析内复用类体顶层区间，避免每个成员重复从类体开头扫描；保留注释、字符串和嵌套深度规则。 |
| 调用关系 | 同文件 callable name 索引；跨文件按名称惰性建立语言/owner 索引，保留 exact 优先、Impl 回退、模块、自身排除及歧义规则。 |
| HTTP / LSP 匹配 | 未匹配请求诊断复用端点路由索引；最近行定位用线性选择代替排序；诊断 ID 使用本次构建的 Set。 |
| 图查询 | 节点/搜索索引按需建立；无关键词请求链列表跳过节点 Map，仅保存限制内项目，仍计算完整匹配总数。 |
| LSP 接收 | 受限倍增缓冲替代分片累计复制，完整消息头只解析一次，大缓冲闲时释放；保留协议和容量上限。 |
| LSP 能力 | 同会话内只缓存明确 method-not-found 的调用层级拒绝，保留能力遗漏时兼容探测、超时重试与 partial 状态。 |
| Utility 取消 | 启动等待立即响应取消；进程启动继续受超时监管，下次任务可复用，已取消任务不发布 analyze。 |
| 快照精简 | 单次调用内复用条目 JSON 字节数和边索引，保留入口测量、最终完整 UTF-8 字节检查以及独立传输/磁盘边界。 |
| 缓存与增量合并 | 配置失效在深层遍历前拒绝；路径规范化仅在一次增量合并内复用，仍区分 repository/worktree。 |
| 多仓准备 | Git 状态查询最多四路并发，结果按输入顺序返回；取消或失败停发新任务，中止并等待在途任务退出。 |
| 图页面 | 出边位置索引替代全图边筛选；拖动只更新相邻边；页面共享节点查找并稳定实际选点回调。 |
| 完整快照读取 | 同一有效代际的并发 full 请求合并，保留失效检查、失败清理和后续重试。 |

## 未消除的成本

- 热分析仍完整读取支持的源码进行哈希，保证内容新鲜度；没有改为只信任 mtime、TTL 或旧指针。
- 单文件 changed 全流程没有稳定提速；缓存载入、图链接和持久化存在固定成本。
- 语义阶段开启时仍保留所需正文，真实 LSP 项目导入、索引和阶段调度未做端到端性能验收。
- 大 JSON 读盘、解析、正常持久化和 IPC 结构化克隆仍存在。未超限快照测量为 188.42→193.26ms，未证明改善；配置失效加载 413.37→406.27ms 也仅确认减少深层遍历。
- 图首次索引仍为 O(N+E)，新增出边位置索引有 O(E) 内存代价；冷索引没有稳定加速。未测峰值 RSS，不声明整体内存降幅。
- 单个复杂文件同步解析、高扇出邻域、部分完整图扫描及请求链重复遍历仍有成本。
- 工作区不是跨文件原子快照；用户可在某文件校验后继续编辑，原有 freshness 规则保留。
