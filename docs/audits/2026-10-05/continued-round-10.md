# 继续确认与修复：第 10 轮

本轮属于 `8e5399f` 之后新启动的十轮检查，与此前 `operation-scenarios.md` 的十一轮分开计数。范围是更新任务执行期间的浏览器跳转失败。

## 问题与原因

- 触发：版本弹窗正在检查或下载安装包，用户点击“打开项目”或“查看 Release”，系统打开浏览器失败。
- 预期：显示打开网页的错误，但更新任务仍显示真实的检查／下载进度；没有用户取消或任务失败时，不能显示更新已经停止。
- 实际：两个跳转入口都调用更新任务的通用失败函数，把 `phase` 改成 `error`。检查／下载并没有取消，稍后仍会完成，安装路径甚至会继续启动安装器。
- 因果链：弹窗的页面按钮在任务运行时可用 → IPC 调用 `openProjectPage`／`openReleasePage` → `openExternal` 拒绝 → 通用 `#fail` 改写活动阶段 → 弹窗根据阶段隐藏下载进度并恢复安装按钮。
- 根因：独立的浏览器操作与更新任务共用失败状态转换，错误反馈与任务生命周期未区分。原有用例覆盖下载失败和正常浏览器跳转，没有覆盖二者并发。

约束依据：`docs/superpowers/specs/2026-09-22-automatic-update-and-release-design.md` 的状态表要求下载中显示字节进度、禁用重复操作；下载期间其他检查不能替换已验证 Release。本次通过受控网络等待确认任务尚未完成，命中“下载中”的前提，因此显示已停止的错误阶段与实际任务状态矛盾。

## 证据与修复

在已有 `storage/data-registry.test.ts` 增加六条用例：

1. 检查中打开项目页失败。
2. 检查中打开 Release 页失败。
3. 下载中打开项目页失败。
4. 下载中打开 Release 页失败。
5. 空闲时打开项目页失败。
6. 空闲时打开 Release 页失败。

前四条使用可控网络等待，在浏览器失败后观察真实服务状态；旧代码全部失败（预期 `checking`／`downloading`，实际 `error`）。后两条作为对照，确认空闲失败仍显示错误且不启动更新。下载使用临时文件，检查实际字节数及 SHA-256；启动安装器和退出均使用 spy，未安装任何软件。

修复为：页面打开失败时仍写入错误消息；若检查或下载任务仍存在，则保留其阶段和提醒状态。实际更新失败继续使用原有失败转换。放行等待后，测试确认检查正常完成，下载完成校验并且启动／退出各调用一次，错误状态清除。

## 验证与边界

- 红阶段：`pnpm exec vitest run apps/desktop/src/main/storage/data-registry.test.ts`，4 失败、20 通过。
- 修复后：同文件 24 条通过；最终联合回归另见十轮汇总。
- 原始日志：`temp/goal-ten-rounds/round-10/red.log`、`green.log`。
- 核对了实际 VersionDialog → IPC → 更新服务的生产入口；故障由受控 `openExternal` 注入，未改变操作系统浏览器关联，也未联网下载或执行真实安装器。
- 排除候选：MCP 在同一 Workspace 内跨仓库查询。设计明确 `projectPath` 只用于只读归属匹配，查询目标包括跨仓库链路，因此没有把跨仓库结果判为缺陷或限制现有行为。
- 未闭环项：系统浏览器自身为何拒绝打开不属于本轮修复范围；它不影响“跳转失败不能误报活动更新已停止”的服务状态判定。
