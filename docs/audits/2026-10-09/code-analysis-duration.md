# 代码分析耗时修复

## RCA 结论

- 状态：计时口径缺陷已确认；未取得用户当时的截图或运行记录，不能逐一核对其具体数值。
- 现象：运行中的执行时间和完成后的耗时采用不同统计范围，完成时可能明显变小。
- 直接原因：页面完成态读取 `snapshot.stats.durationMs`，该值原本由分析引擎产生。
- 根因：应用服务从任务入队开始发布 `startedAt`，但直接把引擎内部耗时作为整个任务耗时，遗漏排队、Git 状态读取、工作进程启动/传输和快照保存。原有页面计时还持续依赖系统墙钟。
- 系统性原因：原有测试分别验证固定 `startedAt` 和固定 `durationMs` 的呈现，没有验证一次任务跨多个阶段的总耗时及恢复后的计时。
- 因果链：接受任务并发布 running → 排队 → 仓库读取 → runner/引擎 → 快照保存 → ready 沿用引擎 stats → 页面展示局部耗时。

## 证据

| 判断 | 类型 | 证据及位置 |
| --- | --- | --- |
| 总耗时没有由服务统计 | 事实 | 修复前 `CodeAnalysisService.#run` 直接使用 runner 返回的 stats；引擎在 `analyze` 内开始计时 |
| 跨阶段耗时被遗漏 | 复现 | 新服务测试控制仓库读取 1 秒、runner 2 秒、保存 3 秒；修复前实际返回固定夹具值 20 ms，期望 6000 ms，测试失败 |
| 修改后统计及恢复一致 | 验证 | 同一测试返回 6000 ms；通过新的 `AnalysisSnapshotCache` 实例恢复后仍为 6000 ms |
| 排队时间属于新任务 | 验证 | 旧任务已执行 10 秒，新任务等待 2 秒、分析 2 秒、保存 3 秒，结果为 7 秒 |
| 后台两个范围采用同一次刷新总耗时 | 验证 | workspace / changed 参数化测试验证保存后的 state、snapshot 和各范围计时一致 |
| 墙钟调整不再使运行计时跳变 | 验证 | 页面测试将墙钟前调一小时、后调两小时，计时仍每次只增加单调时钟经过的一秒 |

## 已排除解释

- 不是毫秒与秒的换算错误：页面按 1000 换算，错误数值在服务返回前已经存在。
- 不是仅刷新页面就能解决的临时显示问题：引擎 stats 原样存入缓存，恢复时继续读取同一局部耗时。
- 不是旧任务的时间应该累计到新任务：新任务从各自被接受时开始计时，排队回归覆盖此边界。

## 修复与防复发

- 应用层以单调时钟记录接受任务到分析图保存结束的耗时；前台和后台任务使用同一口径。
- 最终计时按 scope 单独保存到小型元数据文件，绑定 analysisId 和 generatedAt；无需为更新耗时再次写入大图。
- 缓存加载只应用匹配任务的有效计时；缺失、损坏、超限或过期的元数据不影响图加载。计时写入失败保留结果并给出提示。
- 页面根据服务起点建立初始时间，后续使用单调时钟推进；切换任务时重新建立起点。
- 分析引擎自身也使用单调时钟，避免墙钟调整产生负耗时。
- 保留原来的页面布局与单位显示。

## 异常状态溯源

- 适用约束：新完成任务的页面耗时应覆盖该任务接受后至分析图保存结束的阶段；引擎内部 stats 单独表示引擎耗时时仍是合法值。
- 依据：用户反馈与同一任务执行时间/完成耗时的连续性要求，已落入服务级回归断言。
- 本次场景：控制时钟测试命中跨阶段执行路径；引擎夹具的 20 ms 被直接传播为任务耗时。
- 首次语义错配：服务将 runner stats 用作 ready 状态的任务统计，而不是引擎生成数值本身。
- 调查边界：测试复现了源码缺陷；没有用户原始进程的逐阶段时间证据。
