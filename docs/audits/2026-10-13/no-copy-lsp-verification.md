验证日期：2026-10-13 至 2026-10-14，Windows 本机。

## 当前结论

不复制方案已接入生产代码，尚未打包或安装。源码和已有依赖直接读取；
只有工程配置、索引、下载缓存、编译产物和新生成的源码写入私有目录。
原仓库写入保护仍保留，不再受完整副本的 250000 文件、4 GiB 限制。

Maven、Gradle 和生成代码链路已经实测。真实 SC 已完成一次 2292 文件的全量运行，
但关系图达到上限，且存在查询失败和源码诊断，结果仍为部分覆盖。

没有修改 SC 源码、原目录权限、用户 Maven 仓库或安装目录。
没有提交、推送、重新打包或安装。

## 第一轮结论：直接取消复制不可行

候选方案未通过通用替换验收。直接读取原工程可以工作，写入保护也能生效，
但现有 JDT LS/Maven 导入器在关闭自动构建后仍可能创建原工程输出目录；
启用自动构建后还会清理、写入原工程的编译目录。真实 SC 工作区的目录联接
又会被现有保护启动器拒绝。不能直接删除复制步骤，也不能关闭保护作为修复。

第一轮只增加临时验证程序和本记录，没有修改生产实现、当前安装包、
SC 源码、SC 目录权限或用户现有分析缓存。

## 第一轮观测结果

### 写入保护与退出

不复制测试工程时，以下八种写入均被拒绝：
覆盖原文件、新建原目录文件、删除原文件、重命名原文件、新建原目录子目录、
通过运行目录内的原文件硬链接写入、长路径文件写入、构建子进程写入。

普通文件及超过 260 字符路径的文件仍可读取，独立运行目录可写。
测试原目录保持不变。另行启动 detached 子进程，终止测试宿主后，
确认该子进程同时退出。

这些结果只证明本次构造的写入与退出场景，不代表任意恶意程序、
外部 daemon 或动态改变链接的场景已经全部验证。

### TypeScript、Vue、Python

| 场景 | 副本基线 | 不复制模式 |
| --- | --- | --- |
| TypeScript 两文件互相引用 | 连接成功，2 个符号 | 相同，跨文件调用指向原源码 |
| Vue 单文件组件 | 连接成功，4 个结构符号 | 相同 |
| Python 两文件互相引用 | 连接成功，2 个符号，覆盖标记 partial | 相同，跨文件调用指向原源码 |

不复制模式三种语言合计约 3.8 秒，测试运行目录未产生文件，原工程保持不变。
时间和空间仅是这个小样例的结果，不代表真实大工程的性能。

Python 的 partial 来自服务器未提供全部类型等关系能力，在副本基线中同样存在。
Vue 样例没有取得跨文件调用关系，因此只能确认结构结果没有退化，
不能据此宣称 Vue 完整语义已经验收。

测试工程包含父 POM、lib/app 两个 Maven 模块、跨模块 `greet()` 调用，

### 已排除的简化方案

1. **整段 `target` 物理路径重定向不可用。** 拦截 Eclipse `LocalFile(File)` 后，
   全新工程样例可以工作，但已有产物和已有生成源码样例失败。预建私有目录并保留
   生成源码输入的第二版仍失败。关键错误是：

   ```text
   Cannot create linked resource '/sample-lib/target/classes'.
   The parent resource is not accessible.
   ```

   物理路径重定向没有保持 Eclipse 资源模型与磁盘目录状态一致，不能使用这一办法。

2. **只处理 Java configurator 的输出目录太晚。** 仅拦截
   `AbstractJavaProjectConfigurator.getFolder` 时，三个样例都在更早的
   `AbstractLifecycleMapping.configure` 中尝试创建原 `target`，被写入保护拒绝。

3. **只隔离编译目录还不够。** 提前调整 Maven Build 模型后，普通、已有产物、
   已有生成源码、自定义输出样例一度都显示 `connected/complete`，调用关系也可解析，
   但 JDT 内部日志仍有：

   ```text
   !ENTRY org.eclipse.jdt.apt.core 4 1 ...
   !MESSAGE Failed to ensure existence of generated source folder annotations
   Cannot create file, access denied: <测试原工程>\lib\code.
   ```

   APT 的设置需要项目相对资源路径，直接传入重定向后的绝对路径会被错误解释。
   此外，已有 `.project/.classpath` 时，JDT 默认元数据处理仍会涉及原文件写入。

这也暴露了当前结果判断的盲点：本次实验出现过内部 APT 错误而客户端仍标记
`complete`、无 warnings。该标记不能证明工程导入和代码生成完整成功。
本轮没有修改生产状态报告逻辑；最终验证额外检查了 `.metadata/.log`
中 severity 4 的错误条目及实际生成产物。

### 最终实验适配方式

1. 在 `AbstractLifecycleMapping.configure` 入口读取已解析的 MavenProject，
   确认 basedir 属于已准入的源根，在内存中把 Build 的 `directory`、
   `outputDirectory`、`testOutputDirectory` 改为独立运行目录。
   不修改 POM，不改变源码目录、已有生成源码输入或依赖坐标。
2. Java configurator 获取输出资源时，返回指向私有目录的 Eclipse linked resource。
   这是私有 Eclipse 元数据中的资源引用，不是在源目录新建 Windows 联接。
3. 借助 JDT 的元数据文件系统，把工程配置存入私有区。
   原配置存在时只初始化上述四类配置缓存；通过独立输入/输出流写入，
   不继承原文件权限，也不修改原配置。
4. 在 `AptConfig.setGenSrcDir/setGenTestSrcDir` 处，将生成目录注册为
   `.gitnest-probe-generated-main/.gitnest-probe-generated-test` 项目相对资源，
   实际位置分别为私有 `generated-main/generated-test`。
5. 原源码路径仍直接作为 LSP 文档 URI；保持受限 token、完整性边界及 Job Object。
   私有输出目录可写，原工程仍不可写。

这是验证可行性的、依赖特定内部类和方法的字节码实验，不是可直接发布的实现。

### 目录联接的目标检查

原生实验启动器只改变原目录遍历规则，未放宽运行目录规则或低完整性写入保护：

- 读取 reparse tag，只接受 junction `0xA0000003` 和 symlink `0xA000000C`。
- 打开真实目标，通过 `GetFinalPathNameByHandleW` 解析后继续检查目标及父目录的
  Medium 写入边界；本原型拒绝 UNC 目标。
- 对已访问目录去重，避免联接环路。
- 私有运行目录仍拒绝联接；受限 token、长路径处理及 Job Object 保持不变。

`junction-guards` 实验结果：

| 场景 | 实际结果 |
| --- | --- |
| 通过合法联接读取文件 | 读到 `dependency` |
| 主进程经联接写入原目标 | 拒绝，文件内容不变 |
| 子进程经联接写入原目标 | 拒绝，文件内容不变 |
| 目录联接环路 | 遍历完成，没有无限递归 |
| 联接指向允许 Low 进程写入的目录 | 准入退出码 127 |
| 私有运行目录自身包含联接 | 准备阶段退出码 127 |

最初尝试用 `icacls` 创建 Low 负例时得到 Access denied，没有降低真实目录权限。
随后改用本次启动器自身建立的 Low 临时目录作为负例目标，完成拒绝验证。

真实 SC 工作区使用同一实验启动器检查所有实际目标：
退出码 0、stderr 为空、stdout 为 `admitted without copying or building`，
耗时 33716 ms。只启动了输出确认文字的进程，没有启动 SC LSP 或构建。
这只证明本次静态目录状态可安全准入；没有验证并发替换联接等时序场景。
